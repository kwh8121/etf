## 1. 권장 개발 방법

이 프로젝트에는 다음 네 가지를 결합한 방식이 가장 적합하다.

1. **점진적 상세화:** 전체 MVP를 한 번에 세부 설계하지 않고, 착수할 마일스톤 하나만 실행 가능한 수준으로 구체화한다.
2. **계약 우선 설계:** 구현 전에 입력, 출력, 오류, 저장, 멱등성, 보안 및 관측 계약을 고정한다.
3. **수직 기능 분할:** API, DB, UI 같은 기술 계층별 대형 작업 대신 하나의 사용자·운영 동작을 끝까지 검증 가능한 단위로 완성한다.
4. **TDD:** 각 기능을 RED → GREEN → REFACTOR 순서로 구현하고, 최신 검증 결과가 있을 때만 완료 처리한다.

전체 흐름은 다음과 같다.

```text
마일스톤 계약 확정
  → 파일·인터페이스 설계
  → RED–GREEN 태스크 분해
  → 요구사항·테스트 추적 검토
  → 구현
  → 요구사항 리뷰
  → 코드 품질·보안 리뷰
  → 전체 검증
  → 다음 마일스톤 계획 구체화
```

## 2. 계획 문서 계층

문서별 책임은 다음과 같이 구분한다.

```text
MVP 기획서
  └─ 무엇을 만들 것인가

ROADMAP
  └─ 어떤 순서와 출시 경계로 개발할 것인가

마일스톤 구현 계획
  └─ 어떤 파일을 어떤 순서로 변경하고 검증할 것인가

Linear 실행 원장
  └─ 무엇이 진행 중이고, 차단되었으며, 어떤 증거로 완료되었는가

테스트·실행 기록
  └─ 요구사항을 실제로 충족했는가
```

M0과 M1은 규모가 작고 테스트 기반이라는 같은 목적을 가지므로 하나의 계획으로 묶는다. M2 이후에는 마일스톤별로 별도 계획을 작성한다.

### 2.1 정본과 Linear의 책임 분리

문서와 Linear에 같은 상세 내용을 중복해서 관리하지 않는다.

| 정보 | 정본 | Linear의 역할 |
| --- | --- | --- |
| 제품 범위·수용 기준 | MVP 기획서 | 관련 문서 링크와 요구사항 ID 표시 |
| 단계·의존성·출시 게이트 | ROADMAP | 프로젝트 마일스톤과 진행률 표시 |
| 파일·인터페이스·태스크 절차 | 마일스톤 구현 계획 | 실행 가능한 이슈와 선행 관계 표시 |
| 코드·마이그레이션 | Git 저장소 | 브랜치·커밋·PR 또는 diff 링크 연결 |
| 테스트·lint·build 결과 | CI 또는 실행 로그 | 명령, 종료 코드, 결과 요약 기록 |
| 현재 상태·차단 사유·담당 | Linear | 운영 중인 실행 상태의 정본 |

기획이나 계약을 바꾸는 결정은 먼저 저장소 문서를 수정하고 리뷰한 다음 Linear 이슈에 링크한다. Linear 이슈 설명만 바꾸어 제품 계약을 변경하지 않는다. 반대로 작업 상태, 담당, 의존성, 차단 사유는 Linear를 현재 상태의 정본으로 사용한다.

## 3. 세부 계획을 작성하는 시점과 범위

### 3.1 한 번에 계획할 범위

한 번에 세부화할 범위는 다음 중 하나로 제한한다.

- 하나의 ROADMAP 마일스톤
- 독립적으로 검증 가능한 하나의 수직 기능
- 선행 계약 변경이 없는 작은 작업 묶음

예를 들어 M2 국내 데이터 수집은 내부적으로 다음과 같이 나눈다.

```text
M2 국내 데이터 수집
├─ 날짜 검증
├─ KRX 응답 파싱
├─ KRX 완전성 판정
├─ Kiwoom 인증
├─ ka10099 마스터 수집
├─ ka40004 연속조회
├─ 스냅샷 저장
├─ 일간 수집 오케스트레이션
└─ 25거래일 backfill
```

각 항목은 테스트부터 저장 결과까지 독립적으로 확인할 수 있어야 한다.

### 3.2 전체 세부 계획을 미리 만들지 않는 이유

M2의 구체적인 파일과 타입은 M1에서 선택하는 테스트 러너, 마이그레이션 구조, fixture 위치와 공통 타입에 영향을 받는다. 아직 결정되지 않은 선행 산출물을 추정해 모든 마일스톤을 상세화하면 실행 시점에 계획을 대량 수정하게 된다.

따라서 다음 원칙을 적용한다.

- 현재 마일스톤은 실행 가능한 수준으로 상세화한다.
- 다음 마일스톤은 인터페이스와 선행 조건까지만 유지한다.
- 현재 마일스톤이 검증되면 실제 산출물을 근거로 다음 계획을 상세화한다.

## 4. 구현 전 계약 정의

각 기능은 코드를 작성하기 전에 다음 항목을 정의한다.

- 입력과 전제 조건
- 정상 출력
- 실패·보류·부분 출력
- 저장되는 데이터와 키
- 외부 부작용
- 멱등성 기준
- 재시도 및 중복 처리
- 보안과 자격 증명 경계
- 로그·메트릭·출처 추적 항목
- 자동화 가능한 수용 기준
- 명시적 비목표

### 계약 예시: KRX 스냅샷 판정

```text
입력:
- basDd: YYYYMMDD
- KRX etf_bydd_trd 응답

TRADING_COMPLETE 조건:
- 모든 BAS_DD가 요청일과 일치
- (BAS_DD, ISU_CD) 중복 수가 0
- 필수 필드 완전성 100%
- 직전 유효 거래일 대비 행 수 98% 이상

출력 상태:
- TRADING_COMPLETE
- NON_TRADING
- PUBLISH_PENDING
- PARTIAL
- FETCH_FAIL

금지:
- PARTIAL 데이터를 정상 etf_daily_kr 데이터로 저장
- 잘못된 달력 날짜로 HTTP 요청
- 빈 응답을 근거 없이 NON_TRADING으로 단정
```

계약에 구현을 바꾸는 모호성이 남아 있으면 태스크 분해 전에 해결한다.

## 5. 태스크 분할 규칙

### 5.1 좋은 태스크의 조건

각 태스크는 다음 조건을 만족해야 한다.

- 하나의 관찰 가능한 동작 또는 실패 조건을 다룬다.
- 변경할 파일이 명시되어 있다.
- 선행 태스크와 입력 인터페이스가 명확하다.
- 먼저 작성할 RED 테스트가 있다.
- 예상 실패 이유를 설명할 수 있다.
- 최소 구현 범위를 정의한다.
- 실행할 검증 명령이 있다.
- 완료 여부를 참·거짓으로 판정할 수 있다.
- 병렬 실행 가능 여부와 파일 충돌 여부가 표시되어 있다.

### 5.2 권장 태스크 크기

한 태스크는 가능하면 2~5분 단위의 작업으로 나누되, 기계적인 분할 때문에 의미가 사라지지 않게 한다. 하나의 태스크가 여러 상태, 여러 API, 여러 저장 경로를 동시에 구현한다면 더 작게 나눈다.

피해야 할 태스크:

```text
Task 2 — KRX 수집기를 구현한다.
```

권장 태스크:

```text
Task 2.1 — 존재하지 않는 KRX 날짜 사전 차단

요구사항:
- KRX-DATE-001

파일:
- test/market-data/krx-date.test.ts
- lib/market-data/krx-date.ts

RED:
- 20260230 입력 시 InvalidKrxDate 오류를 기대한다.
- HTTP mock 호출 횟수가 0인지 확인한다.

예상 실패:
- 날짜 검증 함수가 아직 없거나 형식만 검사해 존재하지 않는 날짜를 허용한다.

GREEN:
- YYYYMMDD 형식과 실제 달력 날짜를 검증하는 최소 구현을 추가한다.

검증:
- npm test -- krx-date
- npm run lint

완료 조건:
- 정상 날짜와 윤년 경계 테스트가 통과한다.
- 잘못된 날짜는 네트워크 호출 전에 거부된다.

선행 조건:
- M1 테스트 러너 설정 완료

병렬 실행:
- 공통 날짜 타입 파일을 다른 태스크가 수정하지 않는 경우에만 가능
```

## 6. 마일스톤 구현 계획서 템플릿

각 `docs/plans/implementation/*.md` 문서는 다음 구조를 사용한다.

### 6.1 문서 메타데이터

- 대상 ROADMAP 마일스톤
- 선행 계획과 기준 커밋 또는 기준 상태
- 작성일과 상태
- 관련 기획 요구사항
- Linear 프로젝트와 마일스톤 식별자
- 연결된 상위 Linear 이슈 또는 이슈 생성 기준

### 6.2 목표 결과와 비목표

- 마일스톤 종료 시 사용 가능해야 하는 결과
- 이번 계획에서 구현하지 않을 기능
- 다음 마일스톤으로 미루는 작업

### 6.3 선행 조건

- 필요한 환경 변수
- 필요한 마이그레이션
- 앞선 마일스톤 산출물
- fixture 및 테스트 기반
- 외부 API 계약 확인 상태

### 6.4 계약과 주요 기술 결정

- 입력·출력 타입
- 상태 전이
- DB 키와 제약
- 오류 및 재시도 정책
- 멱등성과 중복 제거
- 자격 증명·로그·RLS 경계
- 관측 메타데이터

### 6.5 파일 변경 지도

예시:

| 파일 | 변경 | 책임 |
| --- | --- | --- |
| `lib/market-data/krx.ts` | 신규 | KRX 요청과 응답 파싱 |
| `lib/market-data/validation.ts` | 신규 | 완전성 판정 |
| `scripts/ingest-kr.ts` | 신규 | 국내 일간 실행 조정 |
| `test/market-data/krx.test.ts` | 신규 | 파서와 계약 테스트 |

파일 경계가 불명확하면 태스크 작성 전에 모듈 책임부터 확정한다.

### 6.6 순서가 있는 실행 태스크

각 태스크에 다음 필드를 포함한다.

- 태스크 ID와 요구사항 ID
- Linear 이슈 식별자 또는 `미생성`
- 목표 동작
- 정확한 변경 파일
- RED 테스트와 예상 실패
- 최소 GREEN 구현
- REFACTOR 허용 범위
- 검증 명령
- 완료 조건
- 선행 태스크
- 병렬 가능 여부와 금지 파일

### 6.7 요구사항 추적표

예시:

| 요구사항 | 태스크 | 테스트 | 완료 증거 |
| --- | --- | --- | --- |
| 잘못된 날짜 무호출 거부 | T2.1 | `krx-date.test.ts` | HTTP 호출 0회 |
| 중복 키 차단 | T2.3 | `krx-validation.test.ts` | `PARTIAL` 반환 |
| `ka40004` 커서 재개 | T2.7 | `kiwoom-pagination.test.ts` | 동일 커서 재시도 |

모든 필수 요구사항은 하나 이상의 태스크와 검증 증거에 연결되어야 한다. 반대로 모든 태스크도 요구사항 또는 명시된 운영 필요에 연결되어야 한다.

실제 실행 계획에서는 `Linear` 열을 추가해 각 태스크를 이슈 식별자와 연결한다.

| 요구사항 | 태스크 | Linear | 테스트 | 완료 증거 |
| --- | --- | --- | --- | --- |
| 잘못된 날짜 무호출 거부 | T2.1 | `ETF-123` | `krx-date.test.ts` | HTTP 호출 0회 |

### 6.8 완료 게이트

```bash
npm test -- <대상 테스트>
npm test
npm run lint
npm run build
```

DB, 외부 API, 워크플로 또는 브라우저 동작이 포함되면 다음 중 해당하는 검증도 추가한다.

- 깨끗한 로컬 DB에 마이그레이션 적용
- RLS 권한 테스트
- fixture 기반 통합 테스트
- 민감정보를 가린 probe
- GitHub Actions 문법 검사와 `workflow_dispatch`
- 인증 사용자와 비인증 사용자의 브라우저 smoke test

## 7. 실제 개발 작업 흐름

각 태스크는 다음 순서로 실행한다.

### 7.1 RED

1. 대응 요구사항과 정확한 실패 조건을 확인한다.
2. Linear 이슈를 `In Progress`로 전환하고 작업 범위와 기준 커밋을 확인한다.
3. 한 가지 동작만 증명하는 테스트를 작성한다.
4. 테스트를 실행한다.
5. 기능 부재 때문에 실패하는지 출력과 종료 코드를 확인한다.
6. 이슈 활동 또는 댓글에 실행 명령, 예상한 실패 이유, 종료 코드를 짧게 기록한다.

구문 오류, 잘못된 fixture, 환경 설정 실패는 유효한 RED가 아니다.

### 7.2 GREEN

1. 해당 테스트를 통과시키는 최소 코드만 작성한다.
2. 대상 테스트를 실행한다.
3. 관련 테스트를 실행해 회귀가 없는지 확인한다.
4. 이슈에 변경 파일, 통과한 대상 테스트와 남은 검증을 갱신한다.

이번 태스크와 무관한 추상화, 미래 기능, 추가 의존성은 넣지 않는다.

### 7.3 REFACTOR

1. 중복, 불명확한 이름, 불필요한 분기를 정리한다.
2. 외부 동작과 계약은 바꾸지 않는다.
3. 대상 테스트와 관련 테스트를 다시 실행한다.

### 7.4 태스크 리뷰

첫 번째 리뷰는 요구사항 준수만 확인한다.

- 요청한 동작이 모두 구현되었는가?
- 범위 밖 동작이 추가되지 않았는가?
- 실패 및 경계 조건이 테스트되는가?
- 국내·미국 시간과 데이터 원천 경계가 유지되는가?

두 번째 리뷰는 코드 품질과 보안을 확인한다.

- 타입, 명명, 모듈 책임이 명확한가?
- 중복과 불필요한 복잡성이 없는가?
- 자격 증명, 로그, RLS 경계가 안전한가?
- 재시도와 멱등성이 운영상 안전한가?
- 테스트가 구현 세부사항이 아니라 동작을 검증하는가?

Critical과 Important 지적은 해당 태스크 또는 마일스톤 종료 전에 수정하고 다시 검증한다.

리뷰가 시작되면 Linear 이슈를 `In Review`로 전환한다. 변경 요청은 이슈를 `In Progress`로 되돌리고 finding과 재검증 범위를 기록한다. 두 리뷰와 필수 검증이 모두 통과하기 전에는 `Done`으로 전환하지 않는다.

## 8. 계획 작성 및 검토 순서

마일스톤 세부 계획은 다음 순서로 작성한다.

1. 기획 정본과 ROADMAP에서 대상 마일스톤 요구사항만 추출한다.
2. 정상, 실패, 보류, 부분, 경계 사례를 먼저 작성한다.
3. 데이터와 API 계약을 확정한다.
4. 파일과 모듈의 책임을 정한다.
5. 테스트 가능한 수직 작업으로 분해한다.
6. 태스크 간 의존성과 병렬 가능 여부를 표시한다.
7. 요구사항과 테스트를 추적표로 연결한다.
8. 요구사항 누락과 범위 확장을 검토한다.
9. 실행 가능성, 파일 충돌, 선행 산출물 가정을 검토한다.
10. 불필요한 추상화와 미래 작업을 제거한다.
11. 첫 RED 테스트부터 계획을 순서대로 실행한다.

### 8.1 요구사항 관점 계획 리뷰

- 기획서의 MUST 항목이 모두 포함되었는가?
- 제외 범위를 침범하지 않는가?
- 국내와 미국의 시간 의미가 섞이지 않는가?
- P1 실패가 국내 P0를 차단하지 않는가?
- 수용 기준마다 테스트 또는 검증 방법이 있는가?
- 초기 스냅샷, 중복 관측, 멱등성 규칙이 누락되지 않았는가?

### 8.2 실행 가능성 관점 계획 리뷰

- 태스크를 문서의 순서대로 실제 실행할 수 있는가?
- 존재하지 않는 타입, 파일 또는 마이그레이션을 가정하지 않는가?
- 같은 파일을 병렬 태스크가 동시에 수정하지 않는가?
- fixture와 테스트 기반보다 구현을 먼저 요구하지 않는가?
- 한 태스크가 너무 많은 상태나 API를 동시에 다루지 않는가?
- 각 태스크의 완료 여부를 명령과 출력으로 판정할 수 있는가?

## 9. 병렬 개발과 서브에이전트 사용

다음 조건을 모두 만족하는 작업만 병렬화한다.

- 입력과 출력 계약이 확정되어 있다.
- 같은 파일, 마이그레이션, 공통 타입, fixture를 수정하지 않는다.
- 한 작업의 결과가 다른 작업의 선행 조건이 아니다.
- 각 작업의 소유 파일과 금지 파일이 명확하다.
- 각 작업을 독립된 테스트로 검증할 수 있다.

적절한 병렬 작업:

- KRX와 Kiwoom fixture의 민감정보 제거 및 경계 사례 작성
- 서로 다른 P0 계산기의 독립 테스트 fixture 작성
- 데이터 계약 리뷰와 RLS·비밀정보 보안 리뷰
- 대시보드 시각 검토와 워크플로 정적 검증

순차로 처리할 작업:

- 스키마 확정 전 수집기와 신호 저장 구현
- 공통 타입 확정 전 여러 파서의 동시 구현
- M2 완료 전 M3 신호 구현
- RLS 확정 전 대시보드 데이터 접근 구현
- 동일 실행 상태를 수정하는 국내·미국 워크플로

서브에이전트 브리프에는 다음만 제공한다.

- 프로젝트 내 작업 위치와 목적
- 요구사항 및 수용 기준
- 소유 파일과 수정 금지 파일
- 선행 인터페이스
- RED·GREEN 및 검증 명령
- 결과 보고 위치와 형식

서브에이전트의 완료 보고는 완료 증거가 아니다. 리더가 Git diff, 테스트 출력과 요구사항 추적표를 직접 대조한다.

## 10. Linear MCP 기반 개발 모니터링

### 10.1 목적과 운영 원칙

Linear MCP는 다음 질문에 실시간으로 답하기 위해 사용한다.

- 현재 어느 마일스톤이 진행 중인가?
- 다음에 실행 가능한 이슈는 무엇인가?
- 어떤 이슈가 무엇에 의해 차단되었는가?
- RED, GREEN, 리뷰, 전체 검증 중 어디까지 진행되었는가?
- 완료된 이슈는 어떤 테스트와 커밋으로 증명되는가?
- 프로젝트가 `onTrack`, `atRisk`, `offTrack` 중 어느 상태인가?

Linear는 진행 상황을 관찰하기 위한 실행 원장이며 코드나 기획 정본을 대체하지 않는다. MCP 연결이 일시적으로 실패해도 로컬 구현과 테스트는 계속할 수 있으며, 연결 복구 후 Git과 실행 로그를 기준으로 상태를 조정한다.

### 10.2 Linear 객체 매핑

Linear의 프로젝트가 로드맵 추적과 마일스톤 기반 진행률을 제공한다는 공식 권장 구조를 따라 다음과 같이 매핑한다.

| 이 프로젝트의 개념 | Linear 객체 | 사용 방법 |
| --- | --- | --- |
| ETF 신호 MVP v2.2 전체 | Project | 범위, 상위 문서, 목표 결과, 건강 상태 관리 |
| M0–M6, R1, R2 | Milestone | ROADMAP 단계와 출시·판정 게이트 표시 |
| 수직 구현 태스크 | Issue | 독립적인 RED–GREEN–REFACTOR·리뷰·검증 단위 |
| 태스크 내부 독립 조각 | Sub-issue | 별도 담당이나 독립 검증이 필요할 때만 사용 |
| 마일스톤 선행 관계 | Issue relation | `blockedBy`와 `blocks`로 실행 순서 표현 |
| 짧은 실행 주기 | Cycle | 팀이 Cycle을 실제 운영할 때만 선택적으로 연결 |
| 영역·유형·우선순위 | Label | 검색과 대시보드 필터에 사용 |
| 주간·게이트 상태 보고 | Project update | 진행률, 건강 상태, 성과, 위험, 다음 작업 기록 |

Cycle은 ROADMAP 마일스톤을 대체하지 않는다. 일정이 없는 개인 개발이나 장기 관측 M6에는 억지로 Cycle을 만들지 않는다.

### 10.3 최초 Linear 구성

개발 착수 시 Linear MCP로 다음 항목을 한 번 구성한다.

1. 기존 팀과 워크플로 상태를 조회한다. 같은 이름의 프로젝트·라벨·마일스톤을 중복 생성하지 않는다.
2. `ETF 일일 신호 시스템 MVP v2.2` 프로젝트를 생성하거나 기존 프로젝트를 연결한다.
3. 프로젝트 설명에 기획서, ROADMAP, 본 실행방안의 저장소 경로 또는 접근 가능한 링크를 기록한다.
4. M0–M6, R1, R2 프로젝트 마일스톤을 생성한다.
5. 워크스페이스의 기존 상태를 우선 재사용해 다음 의미에 매핑한다.
   - `Backlog`: 아직 상세화하지 않은 작업
   - `Ready`: 계약과 선행 조건이 충족되어 시작 가능
   - `In Progress`: RED 또는 GREEN 진행 중
   - `In Review`: 요구사항 또는 코드 리뷰 중
   - `Done`: 완료 정의와 검증 증거를 모두 충족
   - `Canceled`: 범위에서 제거되었고 근거가 기록됨
6. 필요한 경우 다음 라벨을 기존 라벨과 중복되지 않게 만든다.
   - 영역: `area:data`, `area:signal`, `area:ops`, `area:ui`, `area:security`
   - 작업 유형: `type:feature`, `type:test`, `type:bug`, `type:docs`, `type:spike`
   - 우선순위: `priority:P0`, `priority:P1`
   - 게이트: `gate:R1`, `gate:R2`
7. M0–M1 구현 계획의 실행 태스크만 먼저 이슈로 만든다. 아직 상세화하지 않은 M2 이후 태스크를 추정해 대량 생성하지 않는다.

Linear 프로젝트나 이슈를 실제로 생성하는 것은 개발 착수 작업에 포함한다. 이 문서를 수정하는 단계에서는 외부 Linear 상태를 만들거나 변경하지 않는다.

### 10.4 이슈 템플릿

각 구현 이슈 설명은 다음 형식을 사용한다.

```markdown
## 목표
관찰 가능한 단일 결과

## 요구사항
- 요구사항 ID와 기획/ROADMAP 링크

## 변경 범위
- 소유 파일
- 수정 금지 파일

## 선행 조건
- blockedBy 이슈
- 필요한 인터페이스와 fixture

## RED
- 먼저 작성할 테스트
- 예상 실패 이유
- 실행 명령

## GREEN
- 최소 구현 범위

## 리뷰
- 요구사항 준수 기준
- 코드 품질·보안 기준

## 완료 증거
- 대상 테스트
- 전체 테스트
- lint/build
- 커밋·PR 또는 diff

## 남은 위험
- 없음 또는 명시된 후속 이슈
```

이슈 제목은 `[마일스톤][태스크 ID] 동작 결과` 형식을 권장한다. 예: `[M2][T2.1] 잘못된 KRX 날짜를 HTTP 호출 전에 거부`.

### 10.5 상태 전이 계약

```text
Backlog
  → Ready
  → In Progress
  → In Review
  → Done
```

상태 전이 조건:

| 전이 | 필수 조건 |
| --- | --- |
| `Backlog → Ready` | 구현 계획, 요구사항 ID, 소유 파일, 선행 조건, RED 테스트가 명확함 |
| `Ready → In Progress` | 모든 `blockedBy`가 완료되고 작업자가 기준 상태를 확인함 |
| `In Progress → In Review` | RED와 GREEN 증거, 변경 파일, 대상 테스트 결과가 기록됨 |
| `In Review → Done` | 요구사항·품질 리뷰 통과, 필수 전체 검증 통과, 커밋/diff 연결 완료 |
| `In Review → In Progress` | 변경 요청이 있고 finding과 재검증 범위가 기록됨 |
| `어느 상태 → Canceled` | 범위 제외 또는 대체 결정이 정본 문서에 반영되고 이유가 연결됨 |

차단은 상태 이름만으로 숨기지 않고 `blockedBy` 관계와 댓글을 함께 사용한다. 댓글에는 차단 원인, 필요한 해제 조건, 마지막 확인 시각을 기록한다.

### 10.6 개발 중 MCP 업데이트 시점

| 시점 | Linear MCP 작업 | 기록 내용 |
| --- | --- | --- |
| 세부 계획 승인 | 이슈 생성·마일스톤 연결 | 요구사항, 파일, 선행 관계, 검증 기준 |
| 작업 시작 | 상태를 `In Progress`로 변경 | 기준 커밋 또는 기준 상태 |
| RED 확인 | 이슈 댓글 또는 설명 갱신 | 명령, 예상 실패, 종료 코드 |
| GREEN 확인 | 이슈 댓글 또는 설명 갱신 | 변경 파일, 대상 테스트 결과 |
| 차단 발생 | 관계·댓글 갱신 | 차단 이슈, 원인, 해제 조건 |
| 리뷰 시작 | 상태를 `In Review`로 변경 | diff/PR, 리뷰 범위 |
| 변경 요청 | 상태를 `In Progress`로 변경 | finding, 수정 범위, 재검증 명령 |
| 태스크 완료 | 상태를 `Done`으로 변경 | 최종 test/lint/build, 커밋/diff, 남은 위험 |
| 마일스톤 종료 | Project update 작성 | 성과, 미완료, 위험, 다음 마일스톤 |

상태가 바뀌지 않은 사소한 코드 편집마다 Linear를 갱신하지 않는다. 위 표의 의미 있는 경계에서만 업데이트해 모니터링 신호가 활동 로그 잡음에 묻히지 않게 한다.

### 10.7 프로젝트 상태 업데이트

다음 시점에 Linear MCP의 프로젝트 상태 업데이트를 작성한다.

- 마일스톤 시작
- 마일스톤 종료
- R1 또는 R2 게이트 판정
- 1영업일 이상 지속될 차단 발생
- 범위, 일정 또는 핵심 계약 위험 발생
- M6 관측 기간에는 주 1회

상태 업데이트 형식:

```markdown
## 현재 결과
- 완료한 동작과 검증 증거

## 진행 현황
- 완료/전체 이슈
- 현재 마일스톤
- 다음 실행 가능 이슈

## 건강 상태
- onTrack | atRisk | offTrack
- 판정 이유

## 차단 및 위험
- 차단 이슈와 해제 조건

## 다음 작업
- 다음 상태 업데이트 전 완료할 이슈
```

건강 상태 기준:

- `onTrack`: 다음 실행 가능 이슈가 있고 출시 게이트를 위협하는 미해결 위험이 없음
- `atRisk`: 복구 경로는 있으나 외부 API, 보안, 데이터 계약 또는 일정 위험이 게이트에 영향을 줄 수 있음
- `offTrack`: R1/R2 필수 조건을 현재 계획과 권한으로 달성할 수 없거나 핵심 경로가 장기간 차단됨

### 10.8 동기화와 불일치 복구

작업 세션 시작 시:

1. Linear MCP로 활성 프로젝트, 현재 마일스톤, `In Progress`, `In Review`, 차단 이슈를 조회한다.
2. Git 상태와 최근 커밋, 구현 계획의 체크 상태를 확인한다.
3. Linear와 저장소가 다르면 코드·테스트·정본 문서를 근거로 실제 상태를 판정한다.
4. Linear 상태와 댓글을 실제 상태에 맞게 갱신한 뒤 새 작업을 시작한다.

작업 세션 종료 시:

1. 이번 세션의 이슈 상태와 검증 증거를 갱신한다.
2. 미완료 작업은 `Done`으로 바꾸지 않고 다음 정확한 행동을 댓글에 남긴다.
3. 새 차단 관계와 후속 이슈를 연결한다.
4. 마일스톤 경계라면 프로젝트 상태 업데이트를 작성한다.

Linear MCP 쓰기가 실패하면 로컬 작업 기록에 실패 시각과 의도한 변경을 남기고 구현을 계속한다. 복구 후 동일 작업을 중복 생성하지 않도록 제목, 태스크 ID, 기존 이슈를 먼저 검색하고 조정한다.

### 10.9 보안과 기록 제한

Linear에는 다음 값을 기록하지 않는다.

- API 키, OAuth 토큰, Supabase 서비스 역할 키, Telegram 토큰
- `.env` 값 또는 마스킹되지 않은 로그
- KRX·Kiwoom 전체 원본 응답
- 인증 헤더, 쿠키, 개인 식별 정보
- 민감정보가 포함된 CI 로그나 첨부 파일

검증 증거는 명령, 종료 코드, 테스트 수, 실패 수, 마스킹된 요약과 안전한 링크만 기록한다. 민감 로그는 승인된 비공개 저장 위치에 두고 Linear에는 위치와 접근 정책만 연결한다.

### 10.10 Linear 모니터링 완료 기준

각 마일스톤 종료 시 다음을 확인한다.

- [ ] 마일스톤의 모든 필수 태스크가 Linear 이슈와 연결되어 있다.
- [ ] 열린 차단 관계와 이유 없는 `In Progress` 이슈가 없다.
- [ ] `Done` 이슈마다 요구사항, 테스트, 리뷰, 커밋/diff 증거가 있다.
- [ ] 취소·연기된 이슈는 이유와 정본 문서 결정에 연결되어 있다.
- [ ] 프로젝트 상태 업데이트에 진행률, 건강 상태, 위험, 다음 작업이 있다.
- [ ] 구현 계획의 추적표와 Linear 이슈 상태가 일치한다.
- [ ] Linear에 비밀정보나 전체 원본 응답이 없다.

참고한 공식 문서:

- Linear는 로드맵 추적에는 Parent/Sub-issue만 사용하는 것보다 Projects와 Milestones 사용을 권장한다: <https://linear.app/docs/making-the-most-of-linear>
- Projects와 Initiatives의 Updates는 진행 상황과 `onTrack`·`atRisk`·`offTrack` 건강 상태 공유에 사용된다: <https://linear.app/docs/how-to-use-linear-startups-mid-size-companies>
- 워크플로 상태, Cycles, 템플릿, 라벨과 Estimates는 팀 운영 방식에 맞춰 구성한다: <https://linear.app/docs/how-to-use-linear-small-teams>

## 11. 마일스톤 완료 증거

각 마일스톤은 다음 순서로 닫는다.

1. 변경 동작의 대상 테스트
2. 관련 통합 테스트
3. 전체 `npm test`
4. `npm run lint`
5. `npm run build`
6. DB·외부 연동·브라우저 중 해당하는 검증
7. 요구사항 준수 리뷰
8. 코드 품질·보안 리뷰
9. 지적 수정 후 1~8 재실행
10. 실제 diff와 수용 기준의 최종 대조

완료 보고에는 다음을 기록한다.

- 변경 파일과 구현 요구사항
- 실행한 명령과 종료 코드
- 테스트 수와 실패 수
- 수동 또는 E2E 검증 결과
- 해결되지 않은 위험과 운영 예외
- 다음 마일스톤 선행 조건 충족 여부
- Linear 이슈 상태, 열린 차단 관계와 마지막 프로젝트 건강 상태

다음은 완료 증거로 인정하지 않는다.

- “통과할 것 같다” 또는 “코드상 맞다”는 추정
- 이전 작업에서 실행한 오래된 테스트 결과
- 대상 테스트만 실행하고 전체 검증을 생략한 상태
- 서브에이전트가 작성한 성공 보고만 있는 상태

## 12. 첫 번째 상세 계획의 범위

가장 먼저 다음 문서를 작성하고 실행한다.

```text
docs/plans/implementation/M0-M1-foundation-plan.md
```

4. fixture 디렉터리와 민감정보 제거 규칙
5. 환경 변수 이름, 사용 위치와 로그 마스킹 계약
6. Supabase 마이그레이션 디렉터리와 핵심 테이블 생성
7. 기본 키, 외래 키, 상태, 시장, `screen`, 콘텐츠 조회 인덱스 테스트
8. KRX 날짜 검증의 첫 RED 테스트
9. 대상 테스트, 전체 테스트, lint와 build 검증
10. Linear 프로젝트·M0–M1 마일스톤·실행 이슈 구성과 첫 프로젝트 상태 업데이트

M0–M1의 실제 산출물과 인터페이스가 검증된 뒤 다음 계획을 작성한다.

```text
docs/plans/implementation/M2-kr-market-data-plan.md
```

## 13. 첫 실행 백로그

실제 개발 착수 순서는 다음과 같다.

1. 기준선 `lint`와 `build` 실행 및 결과 기록
2. Linear MCP 연결, 기존 팀·상태·프로젝트·라벨 조회
3. Linear 프로젝트와 M0–M1 마일스톤 구성
4. 기존 코드와 의존성에 맞는 최소 테스트 러너 결정
5. `npm test` 스크립트와 첫 테스트 파일 추가
6. 민감정보 제거 fixture 규칙 수립
7. M0–M1 실행 이슈 생성과 선행 관계 연결
8. 잘못된 KRX 날짜 이슈를 `In Progress`로 전환
9. 무호출 RED 테스트 작성·실패 확인 및 증거 기록
10. Supabase 핵심 스키마 마이그레이션 작성
11. 스키마 제약 및 RLS 경계 테스트 작성
12. 최소 구현으로 대상 테스트 통과
13. 요구사항 리뷰와 코드 품질·보안 리뷰
14. 전체 test, lint, build 실행
15. 완료 이슈의 증거와 상태 갱신
16. M0–M1 프로젝트 상태 업데이트 작성
17. 실제 산출물을 바탕으로 M2 상세 계획 작성

각 항목은 다음 반복으로 완료한다.

```text
실패 테스트 확인
  → 최소 구현
  → 대상 검증
  → 리팩터링
  → 독립 리뷰
  → 전체 검증
```

## 14. 최종 원칙

세부 구현 계획의 목적은 문서를 많이 만드는 것이 아니라 구현자가 추측하지 않고 순서대로 실행할 수 있게 하는 것이다. 각 계획은 다음 질문에 즉시 답할 수 있어야 한다.

- 지금 어떤 동작을 만드는가?
- 어떤 파일을 변경하는가?
- 구현 전에 어떤 테스트가 실패해야 하는가?
- 최소 구현 범위는 어디까지인가?
- 무엇을 실행하면 완료를 증명할 수 있는가?
- 어떤 요구사항과 연결되는가?
- 다음 작업을 시작할 선행 조건이 충족되었는가?
- Linear의 상태와 저장소의 실제 상태가 일치하는가?

이 질문에 답할 수 없는 태스크는 구현 전에 다시 분해하거나 계약을 보완한다.
