# ETF 신호 MVP 세션 연속성·정합성 하네스

> 적용 범위: 개발 작업 시작, 의미 있는 구현 경계, 마일스톤 종료, 세션 종료
>
> 로컬 검사 명령: `npm run continuity:check`

## 1. 목적

이 하네스는 다음 세션이 이전 작업의 결과를 추정하지 않고 이어받도록 한다. 작업 상태는 하나의 도구에만 의존하지 않으며, 정본 문서·Git 검증 증거·작업 기록·Linear·OpenViking 메모리에 역할별로 분리해 남긴다.

성공 기준은 다음과 같다.

- 다음 작업자가 현재 마일스톤, 완료·차단 상태, 다음 정확한 행동을 5분 안에 파악한다.
- 완료 선언마다 최신 검증 증거와 정본 문서 경로가 있다.
- Git, Linear, 작업 기록, 메모리의 상태 불일치를 다음 세션 시작 전에 발견·수정한다.
- 비밀값, 토큰, DB 비밀번호, 원천 API 응답은 어떤 기록 표면에도 남지 않는다.

작업 기록, Linear, 메모리는 제품·데이터 계약을 독자적으로 바꾸지 않는다. 계약 변경은 먼저 정본 계획 문서와 Git에 반영한다.

## 3. 세션 시작 절차

1. `AGENTS.md`의 **ETF 신호 MVP 작업 연속성** 절을 읽는다.
2. OpenViking에서 최신 ETF 신호 MVP 메모리를 recall하고, 경로가 필요한 내용은 실제 저장소 문서로 확인한다.
3. 다음 명령을 실행해 로컬 연속성 전제 조건을 확인한다.

   ```bash
   npm run continuity:check
   ```

4. Git 작업 트리와 최신 `docs/jobs/` 기록을 확인한다. 관련 없는 사용자 변경은 수정·stage·되돌리지 않는다.
5. Linear에서 활성 프로젝트, 모든 마일스톤의 **이름·설명·진행률**, `In Progress`·`In Review` 이슈, 차단 이슈와 최신 프로젝트 update를 조회한다. ROADMAP의 마일스톤 ID/명칭/완료 상태 표와 한 항목씩 대조한다.
6. Git·정본 문서·Linear가 다르면 코드와 최신 검증 결과를 근거로 실제 상태를 판단한다. Linear의 프로젝트 상태·요약·마일스톤 명칭·완료 이슈 연결·이슈 본문·최신 project update를 한 번에 보정한 뒤 **read-back 조회**로 진행률과 다음 작업이 정본과 일치하는지 확인하고 구현을 시작한다.

## 4. 구현 경계의 기록 규칙

다음 사건에서 기록을 갱신한다.

| 사건                     | 정본/Git              | 작업 기록         | Linear                 | OpenViking 메모리        |
| ------------------------ | --------------------- | ----------------- | ---------------------- | ------------------------ |
| 작업 시작                | 기준 commit·범위 확인 | 선택 사항         | `In Progress`          | 불필요                   |
| RED/GREEN 또는 계약 확정 | 테스트·코드·계획 갱신 | 명령과 요약       | 댓글 또는 설명 갱신    | 불필요                   |
| 외부 연결·migration·배포 | 실제 서비스 결과      | 적용 ID·검증 결과 | 이슈 증거·차단 갱신    | 다음 세션에 영향 시 저장 |
| 마일스톤 종료            | 계획 상태·추적표 갱신 | 필수              | `Done`, project update | 필수                     |
| 세션 종료                | diff·검증 결과 확인   | 필수              | 열린 이슈의 다음 행동  | 필수                     |

사소한 편집마다 외부 도구를 갱신하지 않는다. 테스트 결과, 상태 전이, 외부 부작용, 차단, 마일스톤 경계처럼 의미 있는 사건만 기록한다.

## 5. 기본 개발 실행 루프와 중단 기준

기능·수정 작업은 아래 순서를 하나의 연속된 작업 단위로 실행한다. 앞 단계의 실패는 원인을 고친 뒤 같은 단계부터 재개하며, 사용자의 별도 확인을 기다리지 않는다.

1. **TDD:** 실패하는 가장 가까운 테스트를 먼저 작성·확인한다.
2. **구현:** 테스트를 만족하는 최소 변경을 적용한다.
3. **포맷:** 변경 파일의 형식을 정리한다.
4. **대상/전체 테스트:** 대상 테스트를 먼저 실행하고, 이어 전체 테스트를 실행한다.
5. **정적 검증:** `npm run lint`, 필요한 경우 `npx tsc --noEmit`, `npm run build`를 실행한다.
6. **리뷰:** 변경 범위에 맞는 코드 리뷰와 회귀·운영 위험 검토를 수행한다.
7. **기록:** 작업 기록, 정본 문서, Linear, OpenViking 메모리를 이 문서의 역할 분리에 맞춰 갱신한다.
8. **통합:** 검증 증거를 확인한 뒤 원자적 커밋과 푸시를 수행한다.

다음은 **중요 이슈**로 분류해 즉시 구현을 멈추고 현재 증거, 영향, 최소 두 가지 대안을 보고한 뒤 승인받는다.

- 운영 데이터 변경·삭제, migration 적용, 비가역 외부 부작용
- 자격 증명·권한·보안 경계 또는 비밀 노출 가능성
- 요구사항·데이터 계약의 해석이 둘 이상으로 갈려 결과가 달라지는 경우
- 반복 재현되는 테스트/배포 실패로 안전한 원인 규명이 불가능한 경우

그 밖의 안전하고 되돌릴 수 있는 로컬 편집·검증·문서화·추적 작업은 자동으로 계속한다.

## 6. 세션 종료 트랜잭션

세션 종료 전 아래 순서를 따른다. 앞 단계가 실패해도 다음 단계를 건너뛰어 완료라고 하지 않는다.

1. **증거 수집:** 대상 테스트, `npm run lint`, 필요한 경우 `npx tsc --noEmit`, `npm run build`, `git diff --check`를 실행한다. 실행할 수 없는 검증은 원인과 대체 증거를 기록한다.
2. **작업 기록 작성·갱신:** `docs/jobs/YYYY-MM-DD-<주제>-작업기록.md`에 결과, 변경 파일, 검증, 외부 적용 ID, 차단, 다음 작업을 기록한다.
3. **정본 상태 반영:** 구현 계획·로드맵의 상태와 추적표를 실제 증거에 맞춘다.
4. **Linear 동기화:** 이슈 상태·마일스톤 연결·마일스톤 명칭/진행률·댓글·차단 관계·프로젝트 상태와 health update를 실제 상태로 갱신한다. 갱신 직후 프로젝트와 완료 이슈를 다시 조회해 ROADMAP의 완료/다음 단계와 일치하는지 확인한다. 비밀값과 원천 응답은 기록하지 않는다.
5. **메모리 저장:** OpenViking에 정본 경로, 완료/미완료, 중요한 외부 상태, 다음 정확한 작업만 저장한다.
6. **로컬 하네스 검사:** `npm run continuity:check`가 필수 정본, 최신 작업 기록, diff 무결성을 통과하는지 확인한다.

Linear 또는 OpenViking 연결이 실패하면 작업 기록에 실패 시각·의도한 변경·재시도 조건을 남긴다. 로컬 정본과 증거를 먼저 완성하고, 다음 세션 시작 시 외부 상태를 중복 생성하지 않도록 기존 항목을 검색해 동기화한다.

## 7. 작업 기록 최소 템플릿

```markdown
# <주제> 작업 기록

> 작업일: YYYY-MM-DD
> 상태: 완료 | 진행 중 | 차단

## 결과

- 완료한 동작과 범위

## 검증

- `<명령>`: 통과 | 실패 | 미실행(사유)

## 외부 상태

- Supabase migration / Linear 이슈 / 배포 ID의 안전한 식별자만 기록

## 차단·위험

- 원인, 영향, 해제 조건

## 다음 작업

1. 다음 정확한 행동
```

## 8. 로컬 검사기의 역할과 한계

`scripts/continuity-harness.mjs`는 다음을 JSON으로 출력하고 실패 시 종료 코드 1을 반환한다.

- 필수 정본·하네스 문서 존재 여부
- 최신 작업 기록 존재 여부
- `git diff --check` 결과
- 작업 트리 요약
- 다음 세션에서 수행할 외부 동기화 행동

이 명령은 Git·문서 상태만 검사한다. OpenViking 메모리 저장과 Linear 갱신은 MCP 인증·의미 판단이 필요한 작업이므로 에이전트가 이 문서의 순서에 따라 수행하고 결과만 기록한다.
