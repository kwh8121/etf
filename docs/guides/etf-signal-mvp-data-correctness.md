# ETF 데이터 정확성 검증·정정 경계

## 확인된 문제와 검증 구분

2026-10-15 읽기 전용 전수 대조에서 KR 수집 원천과 정규화 일별 데이터는 일치했으나 신호 계산 입력이 Supabase 기본 반환 한도 1,000행에 잘렸다. 같은 제한이 master 조회에도 있어 기존 종목을 새 종목으로 오인했다. 따라서 기존의 고정 8유형 × 10행 검증 성공은 내용의 정확성을 보장하지 않는다.

| 계층 | 확인 내용 | 기존 감사 결과 |
| --- | --- | --- |
| 원천 보존 | Storage 다운로드·SHA-256·날짜 | 74개 고유 객체 오류 0 |
| KR 정규화 | 원천과 15개 필드·코드·날짜 | 39거래일 45,562행 불일치 0 |
| KR 신호 | 전체 입력 재계산 후 코드·순위·값 | 최신 고정 신호 코드 14개 교체, 공통 코드 순위 16개 차이 |
| KR turnover | 직전 20거래일 전체 입력 | 최신 기대 13행, 저장 0행 |
| 신규 판정 | 이벤트 이전 master snapshot의 코드 존재 | 223이벤트 중 214개가 이미 존재 |
| US 신호 | 저장 원천 전체 replay | 7 run·60,250행 일치; 외부 전체 종목 포괄성은 별개 |

이 수치는 수정 전 감사 시점의 증거다. 이후 검증 결과와 운영 정정 여부를 혼동하지 않는다.

## 정정 원칙

- 자동으로 수행하는 범위는 코드·회귀 테스트·읽기 전용 감사·전후 차이 제안이다.
- 운영 데이터 변경은 별도 승인 대상이다. 승인 시에도 대상 run·snapshot·행 키·변경 값이 고정된 제안과 적용 직전 재조회가 필요하다.
- 정정 전 대상 행과 run metadata를 복원 가능한 형태로 보존한다. 백업에도 비밀값·원천 응답을 문서화하지 않는다.
- 보고 표식 `notes.telegram_reported_at`과 관측 시각은 보존한다. 과거 보고가 새로 발송되거나 관측 횟수로 중복 집계되지 않게 한다.
- 과거 Telegram은 기본적으로 재발송하지 않는다. 정정된 웹·DB와 이미 발송된 메시지의 차이는 운영 기록에 남긴다.
- 당시 calendar sequence와 현재 정본이 달라지거나 run 입력이 교체된 snapshot을 가리키면 재현 불확실 사례로 분리한다. 최신 정본 기준 재계산을 당시 값의 확정적 정정으로 단정하지 않는다.
- 최초 master snapshot의 종목은 최초 관측이지 신규 상장의 증명이 아니다. 이른 snapshot 코드 존재는 false-positive의 근거이고, 처음 나타났다는 사실만으로 실제 IPO를 확정하지 않는다.

### 운영 적용 전 체크포인트

읽기 전용 제안은 적용 스크립트가 아니다. Q-27 승인이 나면 다음 조건을 충족한 최소 적용 경로를 별도로 검증한다.

과거 `signals:kr-price`·`daily:kr`의 단순 재실행을 정정 경로로 사용하지 않는다. 현재 listing 알림 상태와 과거 상태가 다르고 신호 행의 관측 시각·metadata가 바뀔 수 있기 때문이다. 추가되는 행의 관측 시각도 원 실행 기준을 명시적으로 정해야 한다.

1. 적용 직전 대상 행·run metadata·원천 hash·calendar source set을 다시 읽어 제안 생성 이후 변동이 없는지 확인한다. 달라지면 제안을 재생성하고 적용을 중단한다.
2. 대상 신호·event·master와 보고 표식을 비공개 백업하고 복원 절차를 확인한다. 사용자 자격 증명을 로그에 출력하지 않는다.
3. 가능하면 트랜잭션으로 적용한다. REST 개별 쓰기만 가능한 경우에는 부분 완료 노출을 막는 상태 전이·실패 복구 경로를 먼저 테스트한다. DB 연결 권한이 필요하면 별도 승인을 받는다.
4. false-positive event의 단순 삭제가 다음 수집에서 다시 생성되지 않도록 master 최초 관측일·event·과거 신호 정정 순서와 참조 관계를 함께 검증한다.
5. 재계산 감사·기존 candidate 검증·보고 표식 보존을 읽기 전용으로 재확인한다. 검증 실패 시 발송하지 않으며 백업으로 복원하거나 승인된 보류 상태를 유지한다.
6. 당시 입력이 재현되지 않는 과거 run은 별도 보류 목록으로 유지한다. M6 누적도 재검증된 근거만 재확정한다.

## US 범위 검토

저장된 원천 범위 내 값의 정확성과 미국 전체 ETF 포괄성은 다른 주장이다. `usa10104` ETF/ETN 목록·ETN 제외·연속조회·중복 제거·5일 가격 정규화는 기존 계약을 유지한다.

현행 `usa20931` 요청은 `stk_cnd=1`이다. 저장소 API 명세에서 `0`은 전체, `1`은 증100%, `2`는 증50%다. 따라서 현재 검증 성공을 전체 미국 ETF를 빠짐없이 비교했다는 뜻으로 표시하지 않는다. 요청 값을 조용히 바꾸지 않는다.

권장 후속: 별도 승인된 제한적 비교 호출로 같은 관측 시점의 `stk_cnd=0`·`1` 결과 차이와 비용·실행 시간을 확인하고, 계약 변경 여부를 결정한다. 이 단계에는 신규 Kiwoom 요청과 향후 저장·보고 범위 변경이 포함되므로 현재 읽기 전용 정정안 작업과 분리한다. `tm_tp=3, tm=2`는 저장 명세상 5일 전을 뜻하며 임의로 기간 오류로 취급하지 않는다.

## 운영 수용 기준

1. 입력 페이지의 exact count·고유 키·날짜별 원천 건수가 맞는다.
2. 부분 입력에서는 run을 완료하거나 보고하지 않는다.
3. 가격·turnover 계산 결과의 구성·순위·수치가 저장 내용과 일치한다.
4. master 최초 관측일이 일반 갱신으로 덮어써지지 않는다.
5. 정확성 감사 실패를 기존 행 수 검증 성공으로 상쇄하지 않는다.
6. 정정 승인 전에는 운영 데이터가 정상화됐다고 완료 선언하지 않는다.

## 검증 실행과 판정 경계

- `npm run verify:data -- latest`: KR·US 최신 완료 run의 저장 원천과 재계산 결과를 대조한다.
- `npm run verify:data -- all --output /tmp/etf-data-accuracy.json`: 전체 완료 run과 신규 판정 이력을 읽기 전용으로 검사하고 로컬 정정안 JSON을 만든다. 운영 적용 옵션은 없다.
- 감사의 불일치 종료 코드와 도구 실행 오류를 구분한다. 기존 운영 KR 불일치는 예상된 발견이며, 성공으로 바꾸기 위해 검사를 완화하지 않는다.
- 실제 CLI는 저장소의 Node 22.23.2 strip-only 명령으로도 확인한다. Vitest·TypeScript 성공만으로 운영 CLI 실행 가능성을 확정하지 않는다.
- `npm run build`는 기존 `next/font/google`의 Geist 다운로드에 네트워크가 필요하다. 제한 환경의 글꼴 fetch 실패를 데이터 로직 오류와 혼동하거나 관련 없는 UI 수정으로 우회하지 않는다.
- 발송 게이트는 현재 run뿐 아니라 랭크 변동에 쓰는 직전 run도 확인한다. 따라서 과거 오류 정정 전에는 새 보고가 차단될 수 있다. 차단을 해제하기 위해 과거 오류를 숨기거나 비교 정보를 임의로 생략하지 않는다.
- KR은 전역 신규 판정 이력의 false-positive·master 최초 관측일·원천 근거도 별도로 검사한다. run 단독 replay는 당시 저장된 신규 종목의 구성 재현이지 신규 상장 사실의 증명이 아니다. 전역 정정 필요 상태에서도 보고·candidate를 성공으로 처리하지 않는다.

## 남은 한계

master 최초 관측일은 기존 DB 행을 전체 재조회하는 저장 경계에서 보존한다. 동시 쓰기까지 DB 자체에서 불변으로 보장하는 trigger·RPC·migration은 이번 범위에 포함하지 않았다. 운영 수집의 중복 실행을 피하고, 별도 동시성 보장이 필요하면 스키마·권한 영향과 함께 승인받는다.

과거 KR 정정 전에는 웹의 기존 저장 내용도 그대로 남는다. 코드 배포만으로 과거 메시지·웹 데이터가 정상화됐다고 표시하지 않는다. 읽기 전용 제안·승인 범위는 `docs/references/2026-10-15-data-accuracy-correction-proposal.md`를 따른다.
