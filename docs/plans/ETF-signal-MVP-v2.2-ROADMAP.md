# ETF 일일 신호 시스템 MVP v2.2 개발 로드맵

> 작성일: 2026-09-18 KST
> 기획 정본: `docs/plans/ETF-signal-MVP-plan-v2.2.md`
> 개발 방법론: `docs/references/Superpowers 스킬 요약-Codex.md`
> 문서 성격: 승인된 MVP v2.2를 구현·검증·운영하기 위한 실행 로드맵
> 우선순위: 국내 P0 운영 가능 상태를 먼저 완성하고, P1은 독립된 실험 트랙에서 검증한다.

## 1. 목표 결과

국내 상장 ETF의 일일 종가 데이터를 검증·저장하고, 매일 사람이 검토할 P0 탐색 신호를 생성해 Telegram과 인증 대시보드로 제공한다. 모든 결과는 입력 스냅샷과 변환 버전까지 추적 가능해야 하며 자동매매나 매수·매도 추천으로 표현하지 않는다.

MVP의 핵심 완료 상태는 다음과 같다.

- KRX 국내 ETF 일일 스냅샷과 Kiwoom ETF 마스터를 실패 시 차단하는 계약으로 수집한다.
- 국내 일간·5거래일 등락, 거래대금 급증, 신규 상장 P0 신호를 생성한다.
- 예약 실행, 실패 알림, Telegram 보고서, 인증된 읽기 전용 대시보드를 운영한다.
- 서비스 역할 키는 수집 작업에만 사용하고, 대시보드는 Supabase SSR 인증과 RLS로 읽는다.
- 순설정 추정과 미국 ETF 등락은 국내 P0와 격리된 P1 실험으로 운영한다.
- 완전 거래일 20일의 관측 결과로 P1과 임계값의 유지·조정·폐기를 결정한다.

## 2. 범위와 출시 경계

### MVP 출시 필수 범위

- `source_snapshot`, 국내 거래일, 국내 ETF 일별 데이터, ETF 마스터, 상장 이벤트, 신호 실행·결과 스키마
- KRX `etf_bydd_trd` 국내 일일 스냅샷
- Kiwoom `ka10099` 일간 ETF 마스터와 `ka40004` 주간·수동 교차검증
- 국내 P0 신호 4종
- 25개 완전 거래일 초기 적재
- Telegram 상태·결과 보고
- 평일 예약 및 수동 실행
- 인증 사용자용 읽기 전용 대시보드와 RLS

### 출시 후 실험 범위

- `LIST_SHRS` 변화에 따른 순설정·환매 추정
- Kiwoom 미국 ETF 일간·5일 등락 어댑터
- 20개 완전 거래일 관측과 유용성 판정

### 제외 범위

- 자동주문, 포트폴리오 엔진, 백테스트, 매수·매도 추천
- 분배금·기업행동 조정 총수익률
- 과거 ETF/ETN 종목군 및 상장폐지 이력 복원
- LP 보유분과 투자자 자금 흐름의 귀속 구분
- Kiwoom/KRX 이외의 가격·분배금·펀더멘털 데이터

## 3. 개발 원칙과 실행 규율

이 로드맵의 각 작업은 Superpowers 방식의 다음 규율을 따른다.

1. **작은 작업 단위:** 한 작업은 가능하면 2~5분 단위의 검증 가능한 단계로 분해하고 정확한 파일과 검증 명령을 지정한다.
2. **RED:** 구현 전에 한 가지 동작을 증명하는 실패 테스트를 작성하고, 기능 부재 때문에 실패하는지 확인한다.
3. **GREEN:** 해당 테스트를 통과시키는 최소 구현만 추가한다.
4. **REFACTOR:** 동작을 바꾸지 않는 범위에서 중복과 복잡성을 줄이고 다시 검증한다.
5. **2단계 리뷰:** 작업 결과를 요구사항 준수 관점에서 먼저 검토하고, 그다음 코드 품질·보안·유지보수 관점에서 검토한다.
6. **증거 기반 완료:** 완료 직전에 대상 테스트, 전체 테스트, lint, build를 새로 실행하고 실제 출력과 종료 코드를 확인한다.
7. **체계적 디버깅:** 실패를 재현하고 단일 원인 가설을 검증한 뒤 회귀 테스트와 최소 수정으로 해결한다.
8. **컨텍스트 격리:** 독립 작업을 서브에이전트에 맡길 경우 작업 범위·금지 파일·입출력·검증 기준을 명시한다. 같은 파일이나 선행 산출물을 공유하는 작업은 병렬화하지 않는다.

현재 저장소에는 테스트 러너가 없으므로 M1에서 테스트 기반을 먼저 만든다. 이후 기능 코드는 테스트보다 먼저 작성하지 않는다.

```text
M0 → M1 → M2 → M3 → M4 → R1
                         └──→ M6 → R2
                              ↑
                         M5 ──┘
```

M5 실패는 R1의 국내 P0 운영과 M6의 국내 관측을 중단시키지 않는다.

## 5. 마일스톤별 실행 계획

### M0 — 착수 기준선과 계약 확정

**목표:** 구현 전에 현재 저장소 상태, 환경 경계, 외부 API 계약과 완료 기준을 고정한다.

작업:

- 현재 `npm run lint`, `npm run build` 결과를 기준선으로 기록한다.
- 필요한 환경 변수 이름과 사용 위치를 문서화하되 실제 값은 기록하지 않는다.
- KRX, Kiwoom, Supabase, Telegram의 비밀정보가 서버/작업 환경 밖으로 나가지 않는 경계를 확정한다.
- KRX 유효 거래일 2개, 달력상 유효한 비거래일 1개, 잘못된 날짜 1개의 probe 시나리오를 고정한다.
- Kiwoom `ka10099`, `ka40004` 요청·연속조회·429 재개 계약을 fixture 형태로 정의한다.
- 최초 `ka10099` 실행은 마스터 초기화이며 전체 종목을 신규 상장 이벤트로 만들지 않는다는 규칙을 고정한다.
- GitHub Actions의 KRX 외부 통신이 막힐 경우 실행 위치만 교체하고 데이터·신호 계약은 유지한다.

주요 산출물:

- 환경 변수 예제 및 운영 설정 문서
- 민감정보가 제거된 API fixture 계획
- `scripts/probe.ts`의 테스트 우선 작업 목록

종료 기준:

- 기획 정본의 API ID, 필수 필드, 상태, 시간 의미가 작업 목록에 누락 없이 연결된다.
- 실제 자격 증명, 토큰, 전체 원본 응답이 Git 추적 파일에 없다.
- 기준선 실패가 있으면 제품 변경과 분리해 원인과 영향을 기록한다.

### M1 — 테스트 하네스와 데이터 기반

**목표:** 이후 모든 기능을 TDD로 개발하고 스키마를 반복 검증할 수 있는 기반을 만든다.

작업 순서:

1. TypeScript와 현재 Next.js 구성을 재사용하는 최소 테스트 러너를 선정·설정한다.
2. `npm test`와 대상 테스트 실행 명령을 `package.json`에 추가한다.
3. fixture 디렉터리와 비밀정보 제거 규칙을 만든다.
4. Supabase 마이그레이션 구조를 만들고 다음 테이블을 추가한다.
   - `source_snapshot`
   - `trading_calendar_kr`
   - `etf_daily_kr`
   - `etf_master_kr`
   - `listing_event_kr`
   - `signal_run`
   - `signal_daily`
5. 기본 키, 외래 키, 상태 제약, `screen`, 콘텐츠 조회 인덱스를 검증한다.
6. 인증 사용자 `SELECT` 정책과 수집 작업 쓰기 권한의 경계를 설계하되 UI 구현은 M4에 둔다.

필수 테스트:

- 같은 실행·신호·코드에 `screen='raw'`와 `screen='liquid'`가 공존한다.
- `observation_key`는 고유하지만 콘텐츠 해시는 반복 관측을 허용한다.
- 국내·미국 날짜 필드가 잘못 결합되지 않는다.
- 허용되지 않은 상태나 시장 값이 DB 제약에서 거부된다.

종료 기준:

- `npm test`, `npm run lint`, `npm run build`가 실행 가능하고 통과한다.
- 마이그레이션을 깨끗한 로컬 DB에 적용하고 되돌릴 수 있다.
- 스키마가 기획 정본의 키·추적성·국내/미국 시간 경계를 보존한다.

### M2 — 국내 데이터 수집·저장

**목표:** 검증된 국내 스냅샷만 멱등적으로 저장하고 25개 완전 거래일을 확보한다.

권장 구현 경계:

- `lib/market-data/krx.ts`: 요청, 파싱, 날짜·완전성·무결성 검사
- `lib/market-data/kiwoom.ts`: 토큰, `ka10099`, `ka40004`, 연속조회와 재시도
- `lib/market-data/snapshot.ts`: 정규화, SHA-256, 출처 추적 메타데이터
- `scripts/probe.ts`: 무저장 계약 확인
- `scripts/backfill.ts`: 국내 25거래일 초기 적재
- `scripts/ingest-kr.ts`: 일간 수집·검증·저장 오케스트레이션

작업 순서:

1. `YYYYMMDD`의 실제 달력 유효성을 HTTP 호출 전에 검증한다.
2. KRX 응답 파서와 숫자 정규화를 구현한다.
3. 스냅샷을 `TRADING_COMPLETE`, `NON_TRADING`, `PUBLISH_PENDING`, `PARTIAL`, `FETCH_FAIL`로 분류한다.
4. 날짜 일치, 중복 0, 필수 필드 100%, 직전 유효 행 수 대비 98% 포괄 범위를 강제한다.
5. `LIST_SHRS * TDD_CLSPRC ~= MKTCAP` 강한 항등 감시와 NAV·순자산 보조 분포 감시를 구현한다.
6. `ACC_TRDVAL / ACC_TRDVOL`의 일중 가격 범위 검사를 구현한다.
7. `ka10099` 마스터 적재와 `reg_day`/`first_seen` 분리를 구현한다.
8. `ka40004`를 `cont-yn=N`까지 조회하고 429 후 같은 커서에서 재개한다.
9. 원본의 비공개 객체 경로와 메타데이터를 기록하고 토큰·키·원본 본문을 로그에서 제외한다.
10. 25개 완전 거래일을 적재하고 재실행 멱등성을 확인한다.

필수 RED 시나리오:

- `20260230`은 네트워크 호출 없이 거부된다.
- 응답 행의 `BAS_DD`가 요청일과 다르면 차단된다.
- `(BAS_DD, ISU_CD)` 중복, 필수 값 누락, 숫자 파싱 실패는 `TRADING_COMPLETE`가 아니다.
- 현재일 빈 응답과 과거 비거래일 빈 응답이 구분된다.
- 최초 마스터 실행은 기존 모든 종목의 신규 상장 알림을 만들지 않는다.
- `ka40004` 429 이후 커서가 초기화되지 않는다.

종료 기준:

- 유효 거래일 2개와 비거래일 1개의 계약 probe 결과가 기대 상태와 일치한다.
- 25개 `TRADING_COMPLETE` 거래일 또는 문서화된 예외가 존재한다.
- 저장된 모든 스냅샷에 `observation_key`, API ID, 행·페이지 수, SHA-256, 변환 버전, 날짜·시각이 있다.
- 동일 입력 재실행이 데이터나 이벤트를 중복 생성하지 않는다.

### M3 — 국내 P0 신호와 Telegram

**목표:** 검증된 국내 데이터만으로 사람이 검토할 P0 결과를 생성·저장·보고한다.

권장 구현 경계:

- `lib/signals/kr-daily-movers.ts`
- `lib/signals/kr-five-day-movers.ts`
- `lib/signals/turnover-surge.ts`
- `lib/signals/new-listing.ts`
- `lib/notifications/telegram.ts`

작업 순서:

1. KRX `FLUC_RT` 기준 일간 상승·하락 `raw`/`liquid` 상위 10개를 만든다.
2. 연속 `seq`와 양 끝점이 있는 경우에만 5거래일 가격수익률을 계산한다.
3. 현재일을 제외한 직전 20거래일 평균으로 거래대금 급증을 계산한다.
4. `reg_day`, `first_seen`, `new_in_snapshot`, `first_alerted_at`을 구분해 신규 상장 이벤트를 만든다.
5. `signal_run`과 `signal_daily`에 입력 스냅샷과 버전을 연결한다.
6. Telegram 메시지를 중요도 순으로 구성하고 길이 제한 시 분할한다.
7. 성공, 보류, 부분, 실패 실행 모두 명시적인 상태 메시지를 보낸다.

필수 표시 문구:

- 5거래일 결과: “KRX가 제공한 종가 기준 가격수익률이며 분배금·기업행동 조정 총수익률이 아님.”
- 시스템 전체: 자동매매 또는 매수·매도 추천이 아닌 탐색 결과임을 명시한다.

필수 RED 시나리오:

- 누락된 거래일 `seq`가 있는 종목은 5거래일 순위에 포함되지 않는다.
- 20일 평균에 현재일이 포함되지 않는다.
- `raw`와 `liquid` 결과가 기본 키 충돌 없이 함께 저장된다.
- 초기 마스터와 최근 30일 목록은 정상 신규 상장 이벤트로 반복 전송되지 않는다.
- Telegram 분할 후에도 시장, 기준일, 원천, 실행 상태와 추적 메타데이터가 남는다.

종료 기준:

- P0 4종의 정상·경계·빈 결과 테스트가 통과한다.
- 부분 또는 실패 스냅샷으로 신호를 생성하지 않는다.
- 같은 입력으로 재실행해 중복 알림과 중복 신호가 생성되지 않는다.

### M4 — 예약 운영과 인증 대시보드

**목표:** 국내 P0를 매일 무인 실행하고 인증 사용자가 안전하게 결과를 조회한다.

작업 순서:

1. `.github/workflows/ingest.yml`에 평일 예약과 `workflow_dispatch`를 추가한다.
2. 동시 실행 방지, 타임아웃, 실패 종료 코드, 재시도 범위를 명시한다.
3. KRX·Kiwoom·Supabase 서비스 역할·Telegram 비밀정보를 작업 환경에만 둔다.
4. 인증 사용자용 RLS `SELECT` 정책을 적용하고 익명·타 사용자 접근을 검증한다.
5. 기존 보호 페이지를 다음 섹션의 읽기 전용 대시보드로 교체한다.
   - 최근 실행 상태와 기준 시각
   - 국내 일간·5거래일 등락
   - 거래대금 급증
   - 신규 상장
   - 데이터 품질 경고
6. 기존 `lib/supabase/server.ts`와 인증 JWT를 사용하고 서비스 역할 클라이언트를 UI 경로에 만들지 않는다.
7. `workflow_dispatch`로 수집 → 저장 → 신호 → Telegram → 대시보드의 단일 E2E 흐름을 확인한다.

종료 기준:

- 예약과 수동 실행이 모두 가능하고 모든 실행이 성공 또는 명시적 실패 알림을 남긴다.
- 인증 사용자는 최신 P0 결과를 읽을 수 있고, 비인증 사용자는 보호된다.
- 브라우저 번들, 서버 렌더 로그, Actions 로그에 서비스 역할 키나 API 자격 증명이 없다.
- GitHub Actions에서 KRX 접근이 불가능하면 대체 실행 위치와 동일한 실행 명령을 문서화한다.

### R1 — 국내 P0 MVP 출시 준비 게이트

R1은 다음 항목을 모두 충족할 때 통과한다.

- [ ] 기획 정본의 국내 P0 수용 기준이 자동 테스트 또는 명시된 E2E 증거와 연결되어 있다.
- [ ] 대상 테스트와 전체 `npm test`가 통과한다.
- [ ] `npm run lint`와 `npm run build`가 통과한다.
- [ ] 깨끗한 DB에서 마이그레이션과 RLS 검증이 통과한다.
- [ ] 실제 또는 승인된 비밀정보 환경에서 수동 실행 1회가 끝까지 성공한다.
- [ ] 같은 입력 재실행의 멱등성이 확인된다.
- [ ] 독립 요구사항 리뷰와 코드 품질·보안 리뷰의 Critical/Important 항목이 0개다.
- [ ] 자동매매·추천 오인 가능성과 총수익률 오인 가능성이 UI·Telegram에서 차단된다.

R1 전에는 P1 때문에 국내 P0 출시를 지연시키지 않는다.

### M5 — P1 실험 어댑터

**목표:** P1을 기본 `off` 기능 플래그와 별도 실행 경로로 추가한다.

#### M5-A 순설정·환매 추정

- `(LIST_SHRS_t - LIST_SHRS_t-1) * NAV_t`와 5거래일 이동 합계를 계산한다.
- 누락 `seq`, 큰 기업행동 의심, 강한 항등 이상 행을 제외한다.
- P0 아래 별도 섹션에 “추정 순설정·환매, 실험 항목이며 LP 보유분이 포함될 수 있음.”을 표시한다.
- 국내 P0 저장·알림 실패 여부와 독립적으로 켜고 끌 수 있게 한다.

#### M5-B 미국 ETF 등락 어댑터

- `scripts/ingest-us-movers.ts`와 별도 수동/미국장 종료 후 워크플로를 만든다.
- `usa10104`는 종목군·ETN 필터, `usa20911`은 일간 상승/하락, `usa20511(tm=5)`은 5일 상승, `usa20931(flu_tp=2, tm_tp=3, tm=2)`은 5일 하락에만 사용한다.
- 방향 표시 부호가 붙은 가격은 `abs(value)`로 정규화한다.
- 공식 시장일이 없으면 `market_date=null`을 유지하고 국내 `bas_dd`나 `trading_calendar_kr`를 사용하지 않는다.
- 동일 콘텐츠의 반복 관측은 `duplicate_observation`으로 기록하고 새 신호를 만들지 않는다.
- 미국 실패가 국내 실행 상태, 알림, 최신성에 영향을 주지 않게 한다.

종료 기준:

- 기능 플래그 기본값이 `off`다.
- 미국 워크플로를 강제로 실패시켜도 국내 P0 실행은 성공한다.
- 반복 미국 스냅샷 2건은 관측 행 2개와 기준 콘텐츠 1개를 만들며 신호는 중복 생성하지 않는다.
- P1은 UI와 메시지에서 실험 항목으로 명확히 분리된다.

### M6 — 완전 거래일 20일 운영 관측

**목표:** 임계값이나 P1 지위를 성급히 조정하지 않고 실제 운영 자료를 축적한다.

매 거래일 기록:

- 국내 스냅샷 상태, 행 수, 검증 경고와 KRX/Kiwoom 불일치 코드 수
- P0 유형별 `raw`/`liquid` 신호 수
- Telegram 성공·실패와 메시지 분할 수
- 실행 시간, 재시도, 429, 공표 지연, 장애 원인
- P1이 켜진 경우 P1 신호 수와 중복 관측 수
- 안정적으로 계측 가능한 경우 사람이 실제로 연 조사 건수; 계측 불가 시 0이 아니라 `미수집`으로 기록

운영 규칙:

- 완전 거래일 20일 전에는 거래대금 배수, 유동성 기준, P1 승격 여부를 조정하지 않는다.
- 장애 수정은 재현 테스트를 먼저 추가하고 M1~M5의 검증 게이트를 다시 통과한다.
- `PARTIAL`이나 `FETCH_FAIL`은 완전 거래일 수에 포함하지 않는다.

### R2 — 유지·조정·폐기 결정

20개 완전 거래일 후 다음 결정을 문서화한다.

| 대상 | 유지 | 조정 | 폐기 |
| --- | --- | --- | --- |
| P0 거래대금 급증 | 검토 가능한 신호량과 사례가 안정적 | 반복적으로 0건 또는 과다 발생하며 근거 있는 새 임계값이 있음 | 사람 검토 가치가 없고 합리적 조정으로 해결되지 않음 |
| 순설정 추정 | LP 한계를 감안해도 반복적인 조사 가치가 있음 | 표시·제외 규칙 또는 실험 임계값 보완이 필요 | 해석 위험이 효용보다 큼 |
| 미국 어댑터 | 시간 의미와 중복 제거가 안정적이고 조사 가치가 있음 | 원천별 범위·표시·실행 시각 보완이 필요 | 신뢰할 수 있는 의미나 유동성 맥락을 제공하지 못함 |

결정 결과에는 관측 기간, 완전 거래일 수, 신호량 분포, 품질 경고, 대표 사례, 미수집 지표와 남은 위험을 포함한다. P0 가치가 입증된 뒤에만 별도 기획으로 백테스트나 포트폴리오 기능을 검토한다.

## 6. 병렬화와 역할 분담

의존성과 파일 소유권이 분리된 경우에만 병렬화한다.

병렬화하기 좋은 작업:

- KRX fixture와 Kiwoom fixture의 민감정보 제거·경계 사례 작성
- 서로 다른 P0 계산기의 테스트 fixture 작성
- 데이터 계약 리뷰와 보안/RLS 리뷰
- 대시보드 UI 검토와 워크플로 정적 검증

순차로 처리할 작업:

- 스키마 확정 전 수집기·신호 저장 구현
- 공통 타입 확정 전 여러 파서 구현
- M2 완료 전 M3 계산 구현
- RLS 확정 전 대시보드 데이터 접근 구현
- 국내·미국이 같은 파일이나 실행 상태를 수정하는 작업

서브에이전트 사용 시 구현 담당과 리뷰 담당을 분리한다. 각 구현 작업은 요구사항, 소유 파일, 금지 파일, 테스트 명령, 보고 형식을 포함한 짧은 브리프로 전달하고 결과는 Git diff와 검증 출력으로 독립 확인한다.

## 7. 품질 게이트와 완료 증거

1. 변경 동작의 대상 테스트 실행

완료 보고에는 다음을 남긴다.

“통과할 것 같다”, “코드상 맞다”, 서브에이전트의 완료 보고만으로 마일스톤을 완료 처리하지 않는다.

## 9. 최종 완료 정의

이 로드맵의 MVP 개발은 R1을 통과하면 국내 P0 출시 준비 완료로 본다. 전체 v2.2 실험 주기는 R2의 유지·조정·폐기 결정과 문서 갱신까지 완료했을 때 종료한다.

최종 확인 항목:

- [ ] 국내 수집·P0·Telegram·대시보드의 단일 E2E 흐름이 검증되었다.
- [ ] 실패·부분·공표 대기 상태가 잘못된 신호를 만들지 않는다.
- [ ] 모든 신호가 입력 스냅샷과 버전으로 재현 가능하다.
- [ ] RLS와 자격 증명 경계가 독립 검토를 통과했다.
- [ ] P1은 국내 P0와 운영상 분리되어 있다.
- [ ] 완전 거래일 20일의 관측 기록과 R2 결정 근거가 남아 있다.
- [ ] 새로 실행한 테스트, lint, build의 성공 증거가 있다.
- [ ] 제외 범위가 별도 승인 없이 구현되지 않았다.

## 10. 첫 실행 백로그

실제 개발을 시작할 때는 다음 순서로 착수한다.

1. 기준선 `lint`·`build` 실행 및 결과 기록
2. 테스트 러너 결정과 `npm test` 추가
3. 민감정보 제거 fixture 규칙과 첫 날짜 검증 RED 테스트 작성
4. Supabase 마이그레이션과 스키마 제약 테스트 작성
5. `scripts/probe.ts` 및 KRX 계약 검증 구현
6. Kiwoom `ka10099`·`ka40004` fixture 테스트와 어댑터 구현
7. `scripts/backfill.ts`와 `scripts/ingest-kr.ts` 구현
8. M2 전체 검증 후에만 국내 P0 구현 시작

각 항목은 실패 테스트 확인 → 최소 구현 → 대상 검증 → 리팩터링 → 독립 리뷰 → 전체 검증 순으로 완료한다.
